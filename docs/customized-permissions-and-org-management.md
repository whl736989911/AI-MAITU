# 定制化功能权限与组织管理设计

> 状态：待开发设计
>
> 目的：为同一套平台服务不同企业、部门和员工，通过统一权限模型停用不需要的功能，并确保页面、API 和运行时能力保持一致。

## 1. 背景与目标

平台需要面向不同用户提供定制化能力：有的用户只需要基础对话，有的用户需要专家或功能型智能体，有的用户需要插件、连接器、通道或工作台能力。未授权功能不仅不应出现在页面上，也不能通过直接调用 API、CLI 或运行时工具继续使用。

本方案的目标是：

- 使用一套统一的功能权限模型，不为不同客户重复维护授权系统。
- 支持企业、部门和员工的组织层级管理。
- 让权限同时控制菜单、路由、API、后台任务和运行时能力。
- 支持通道类型级别的授权，并在权限撤销后立即停用对应通道。
- 尽量复用现有用户、角色、组织单元和权限实现，降低迁移风险。
- 第一阶段只实现用户/角色级权限，不增加部署级全局功能开关。

## 2. 已确定的产品决策

### 2.1 组织层级

```text
系统管理员
└── 企业管理员
    └── 部门管理员
        └── 企业员工
```

角色与范围如下：

| 角色 | 权限范围 | 数据管理范围 | 账号管理能力 |
| --- | --- | --- | --- |
| 系统管理员 | 全部功能、全部权限 | 全部企业、部门和用户 | 可创建和管理所有角色 |
| 企业管理员 | 系统管理员授予的权限 | 本企业全部部门和用户 | 只能创建本企业员工 |
| 部门管理员 | 企业管理员授予且自身拥有的权限 | 本部门及所有子部门 | 只能创建本管理范围内的员工 |
| 企业员工 | 被授予的功能权限 | 仅自身可用资源，具体按业务规则限制 | 不能创建账号或授权 |

补充规则：

- 系统管理员天然拥有所有权限。
- 企业管理员和部门管理员不能创建系统管理员或企业管理员。
- 部门管理员的管理范围是“本部门及子部门”，不能管理兄弟部门或上级部门。
- 下级管理员不能授予自己没有的权限。
- “拒绝权限”属于高风险操作，第一阶段只允许系统管理员使用。
- 现有数据库中的 `unit_admin` 值保留，界面显示名称调整为“部门管理员”，避免破坏已有数据。

### 2.2 权限粒度

采用一个统一的权限集合。权限表示“用户是否可以使用某项平台能力”，不额外建立独立的客户产品授权体系。

第一阶段需要覆盖的权限：

| 权限标识 | 功能 | 说明 |
| --- | --- | --- |
| `mbti` | MBTI | MBTI 配置和相关能力 |
| `experts` | 专家 | 专家目录、专家使用和相关管理能力 |
| `features` | 功能型智能体 | 功能型智能体页面和相关能力 |
| `plugins` | 插件 | 插件管理及插件运行能力 |
| `channels` | 通道管理 | 通道管理入口和基础通道能力 |
| `channel_<kind>` | 具体通道类型 | 例如 `channel_feishu`、`channel_dingtalk` |
| `connectors` | 连接器 | 连接器管理及运行能力 |
| `skill_packages` | 技能包 | 技能包管理和使用 |
| `terminal` | 工作台-终端 | 终端能力 |
| `browser` | 工作台-浏览器 | 浏览器能力 |
| `desktop` | 远程桌面 | 远程桌面能力 |
| `acp` | ACP | ACP 相关能力 |
| `users` | 用户管理 | 用户、角色、组织和权限管理 |

专家和功能型智能体必须是两个独立权限：

- 只有 `experts` 时，只显示专家相关功能。
- 只有 `features` 时，只显示功能型智能体相关功能。
- 两项都有时显示两类功能。
- 两项都没有时隐藏两类入口，并由后端拒绝对应 API。

工作台不增加一个强制的总权限：

- 有 `terminal` 时显示终端。
- 有 `browser` 时显示浏览器。
- 两者都没有时隐藏工作台入口。
- 后端仍分别校验 `terminal` 和 `browser`，避免通过工作台聚合入口绕过权限。

### 2.3 通道权限

通道采用“通道管理权限 + 通道类型权限”两级模型：

```text
channels
channel_feishu
channel_dingtalk
channel_wecom
channel_qq
channel_weixin
...
```

规则：

- `channels` 控制是否可以进入通道管理功能。
- `channel_<kind>` 控制是否可以使用某一种通道类型。
- 没有通道类型权限时，不能创建、编辑、删除、测试、绑定或查看该类型通道。
- 已存在的通道在类型权限被撤销后立即停止运行。
- 权限恢复后是否自动恢复通道运行，按实现时的运行时生命周期决定；默认应要求重新加载或由通道管理服务恢复，不能在权限撤销期间继续运行。

### 2.4 停用语义

本方案采用“全链路关闭”：

- 前端不显示未授权菜单、页面、路由、按钮和标签页。
- 后端 API 统一返回无权限错误。
- CLI 或嵌入式调用不能绕过权限检查。
- 后台任务、工具调用和运行时能力必须检查对应权限。
- 插件、连接器和通道等已经配置的能力，在权限撤销后也不能继续运行。

第一阶段不做部署级的配置文件/环境变量模块开关。也就是说，本阶段解决的是“同一实例内不同用户/角色的功能授权”，不是“整个部署是否安装某个产品模块”。

## 3. 当前代码基础

实现时优先复用以下现有能力：

- `src/octop/infra/users/permissions.py`：权限目录、权限解析和授权约束。
- `src/octop/infra/users/identity.py`：用户角色和身份模型。
- `src/octop/api/routers/users.py`：用户创建、角色分配和权限管理接口。
- `src/octop/api/routers/org_units.py`：组织单元及组织范围管理。
- `dashboard/src/utils/permissions.ts`：前端权限判断和导航权限映射。
- `dashboard/src/layouts/sidebarNav.tsx`：侧边栏功能分组。
- `src/octop/api/common/agent.py`：Agent 运行能力 `AgentCapability`。

`AgentCapability` 不替换用户功能权限，两者职责保持分离：

```text
用户权限：用户是否可以使用某个产品模块
AgentCapability：某个 Agent 是否允许使用某项具体运行能力
```

最终运行权限必须同时满足用户权限和 Agent 能力限制。

## 4. 后端设计

### 4.1 权限目录与权限计算

在现有 `PERMISSIONS` 基础上补充 `mbti`、`experts`、`features`、`acp` 以及通道类型权限。

权限计算继续使用现有模型：

```text
有效权限 = 角色基础权限 + 组织单元授权 + 用户授权 - 拒绝权限
```

新增的核心约束：

```text
下级可获得的权限 ⊆ 授权者自身的有效权限
```

权限目录接口应返回：

- 权限标识。
- 显示名称和说明。
- 是否为动态权限。
- 当前操作者是否可以授予该权限。
- 权限所属功能分组。

### 4.2 四级角色和组织范围

新增 `enterprise_admin` 角色，保留现有角色值：

```text
admin             → 系统管理员
enterprise_admin  → 企业管理员
unit_admin        → 部门管理员
user              → 企业员工
```

需要实现：

- 企业管理员的企业范围判断。
- 部门管理员的“本部门及子部门”范围判断。
- 员工的最小资源访问范围判断。
- 列表查询、详情查询、修改和删除操作都使用相同的范围校验。
- 组织归属变更时校验目标组织是否在操作者的管理范围内。
- 角色变更时校验目标角色是否低于操作者可管理的角色层级。

如果现有组织单元已经能够表达企业和部门，应直接扩展现有组织树，不新增平行的企业/部门表。

### 4.3 用户和授权接口

用户管理 API 需要统一执行以下校验：

1. 创建者是否拥有 `users` 权限。
2. 目标组织是否在创建者管理范围内。
3. 目标角色是否为创建者允许创建的角色。
4. 目标权限是否属于创建者自身有效权限。
5. 目标用户是否在创建者可管理范围内。
6. 是否尝试修改系统管理员、企业管理员或其他越权对象。

建议将这些规则放入用户/权限领域服务或通用辅助函数中，路由层只负责请求校验、调用领域逻辑和转换错误，不在各个路由内重复实现层级规则。

### 4.4 功能接口接入

各功能路由按模块接入统一权限：

- MBTI 路由接入 `mbti`。
- 专家路由接入 `experts`。
- 功能型智能体路由接入 `features`。
- 插件管理和插件运行入口接入 `plugins`。
- 连接器管理、MCP 组装和连接器运行入口接入 `connectors`。
- 技能包管理和加载入口接入 `skill_packages`。
- 终端和浏览器分别接入 `terminal`、`browser`。
- 远程桌面接入 `desktop`。
- ACP 全局入口从当前固定管理员判断，调整为与 `acp` 权限模型兼容；涉及系统级危险操作的接口仍可额外要求系统管理员。
- 用户管理接口接入 `users` 和组织范围判断。

### 4.5 运行时权限

运行时必须重新检查权限，不能只依赖页面进入时的结果：

- 插件工具调用前检查 `plugins`。
- 连接器/MCP 调用前检查 `connectors`。
- 通道收发消息前检查对应 `channel_<kind>`。
- 终端、浏览器和远程桌面工具分别检查对应权限。
- 权限撤销后，正在执行的长任务在下一次能力检查时被拒绝或终止。
- 通道权限撤销后，通道消费者停止接收消息，发送入口也必须拒绝。

通道类型目录应集中维护，避免 API 路由、运行时服务和前端分别硬编码一套通道名称。

## 5. 前端设计

### 5.1 统一权限上下文

登录后由前端保存当前用户的有效权限和可管理范围，提供统一方法：

```typescript
hasPermission("plugins")
hasAnyPermission(["terminal", "browser"])
canManageUser(user)
canGrantPermission(permission)
```

菜单、路由、按钮、标签页和页面内操作都使用统一方法，避免出现“菜单隐藏但路由可访问”或“按钮隐藏但 API 仍可调用”的不一致。

### 5.2 导航和路由

侧边栏按权限动态生成：

| 导航分组 | 权限 |
| --- | --- |
| MBTI | `mbti` |
| 专家 | `experts` |
| 功能型智能体 | `features` |
| 插件 | `plugins` |
| 通道 | `channels` |
| 连接器 | `connectors` |
| 技能包 | `skill_packages` |
| 工作台-终端 | `terminal` |
| 工作台-浏览器 | `browser` |
| 远程桌面 | `desktop` |
| ACP | `acp` |
| 用户管理 | `users` |

路由守卫必须与导航使用相同权限判断。直接访问 URL 时，未授权用户应看到统一的无权限状态，而不是空白页面或前端异常。

### 5.3 用户授权页面

用户管理界面根据操作者权限动态限制：

- 可创建的角色。
- 可选择的企业和部门。
- 可查看和管理的用户。
- 可授予的权限。
- 可修改的组织归属。

权限编辑界面应区分并展示：

- 角色基础权限。
- 组织单元授权。
- 用户额外权限。
- 拒绝权限。

下级管理员不能看到或选择超出自身授权范围的权限，但后端仍必须执行最终校验。

## 6. 数据迁移与兼容

迁移原则：尽量保留已有用户、角色、权限和通道行为，避免升级后功能无故消失。

具体处理：

- 新增 `enterprise_admin` 角色支持。
- 保留 `admin`、`unit_admin`、`user` 的已有数据。
- `unit_admin` 的界面显示名称改为“部门管理员”。
- 系统管理员继续拥有全部权限。
- 已有用户的显式权限不直接清空。
- 对已有专家、MBTI 和通道数据执行兼容映射。
- 新增权限没有历史数据时，按升级前行为进行安全回填，再由管理员调整。
- 数据库变更遵循项目现有迁移规则，同时提供 SQLite 和 PostgreSQL 迁移脚本。

## 7. 实施阶段

1. 整理权限目录、角色层级和组织范围规则。
2. 增加企业管理员角色并完善用户管理边界。
3. 接入 MBTI、专家、功能型智能体、插件、连接器等功能权限。
4. 接入工作台、远程桌面、ACP 和用户管理权限。
5. 实现通道类型权限和运行时停用。
6. 改造前端菜单、路由和用户授权页面。
7. 执行数据兼容迁移。
8. 完成越权、兼容和前端回归测试。

## 8. 测试与验收标准

### 后端测试

- 系统管理员拥有全部权限。
- 企业管理员只能使用系统管理员授予的权限。
- 企业管理员不能管理其他企业用户。
- 部门管理员可以管理本部门和子部门，不能管理兄弟部门。
- 企业员工不能创建账号、修改角色或授权。
- 授权者不能授予自己没有的权限。
- `experts` 与 `features` 可以独立生效。
- `terminal` 与 `browser` 可以独立生效。
- 通道类型权限能阻止创建、编辑、删除、测试和绑定。
- 撤销通道类型权限后，已有通道停止收发消息。
- 插件和连接器没有权限时，管理接口和运行时工具都被拒绝。
- AgentCapability 与用户功能权限同时生效。

### 前端测试

- 无权限导航不显示。
- 无权限路由不能进入。
- 工作台根据终端和浏览器权限分别显示。
- 专家和功能型智能体入口独立显示。
- 通道类型选择器只显示授权类型。
- 用户管理页面只显示操作者可以创建的角色和权限。
- 直接输入受限 URL 时显示统一无权限页面。

## 9. 完成定义

本项开发完成的最低标准：

1. 四级角色和组织范围在后端生效，不能通过修改请求参数绕过。
2. 功能权限能控制对应页面、API 和运行时能力。
3. 专家/功能型智能体、终端/浏览器和通道类型权限可以独立配置。
4. 权限撤销后，插件、连接器和通道不能继续运行。
5. 前端导航、路由、按钮和后端权限判断保持一致。
6. 旧用户和旧配置完成兼容迁移。
7. `make all` 和前端 TypeScript 检查通过。

## 10. 明确不在第一阶段的内容

- 不增加部署级全局模块开关。
- 不建立独立于统一权限系统的客户产品授权系统。
- 不把 `AgentCapability` 与用户功能权限合并。
- 不在本项中重构无关的用户、组织或通道业务逻辑。
