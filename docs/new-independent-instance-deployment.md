# 新增独立实例部署指南

## 一、目标与适用范围

在已经运行一套本平台的服务器上，新增一套面向用户体验或测试的独立平台。

**这是新增独立实例，不是升级、迁移、恢复或接管现有平台。** 允许共享服务器资源，但要求两套平台的配置、业务数据、登录状态、授权身份和日常运维互不串用。CPU、内存、磁盘容量、带宽等资源竞争不在本文的隔离承诺内。

本文记录用户已确认的 AIWAY 新实例参数，以及可以直接交给部署 Agent 的提示词。**参数确认不代表目标服务器已经没有冲突，也不代表完成部署验收**：Agent 仍须先只读盘点，无冲突后按方案继续；发生实际冲突或需要额外主机级变更时再暂停询问。

## 二、部署方式与隔离边界

对于开放给不同用户体验的测试平台，优先考虑独立容器部署，不授予宿主机管理权限，也不挂载生产目录或宿主 Docker socket。

如果必须向不可信体验用户开放任意宿主命令、真实桌面、宿主 Docker 管理或其他高权限能力，仅更换目录、服务名和端口不足以建立安全边界，应考虑独立虚拟机。容器仍共享宿主内核，不能据此承诺绝对安全隔离。

主机级依赖升级、Docker 重启、全局安全策略变更、共享反向代理配置错误，以及外部机器人或存储的重复接入，都可能影响现有平台。部署 Agent 必须把这些共享边界纳入检查，不得因为“不考虑资源占用”就忽略它们。

### 已核对的项目特性

- 数据根目录优先读取 `MAITU_HOME`，其次兼容 `OCTOP_HOME`，未设置时使用服务用户的 `~/.maitu`。数据库、Agent、知识库、日志和内部备份等路径由该根目录派生。见 [路径解析源码](../src/octop/infra/utils/paths.py)。
- 原生安装脚本固定写入 `/etc/systemd/system/maitu.service`。只修改数据目录、运行用户和端口，不能保证第二实例安装安全。见 [原生安装脚本](../deploy/ubuntu/install-source.sh)。
- 默认 Compose 显式设置项目名 `maitu`、容器名 `maitu` 和镜像 `maitu:latest`。仅添加 `docker compose -p` 不能消除显式容器名或镜像标签冲突。见 [Compose 配置](../docker/docker-compose.yml)。
- 当前容器入口脚本会设置兼容的 `OCTOP_HOME`。若另行设置 `MAITU_HOME`，必须核对初始化脚本、应用实际数据根和持久化挂载保持一致。见 [容器入口脚本](../docker/docker-entrypoint.sh)。
- 前端使用固定的 `localStorage["auth_token"]` 保存登录令牌，同源不同路径共享该存储。默认应采用独立测试域名，不应只用同一域名下的两个路径区分实例。见 [前端认证请求源码](../dashboard/src/api/request.ts)。独立域名还需检查 Cookie 的 Domain 范围，不能宽泛共享父域。

曾以无写入的路径解析命令核对：不同 `MAITU_HOME` 会分别解析数据库、Agent、知识库和备份目录。这只证明路径解析规则，不替代对目标服务器实际挂载、数据库连接和运行进程的验收。

### 不需要逐个改名的内容

数据根目录隔离后，其中的 `config.json`、`maitu.db`、`agents/`、`knowledge/`、`logs/`、`backups/` 可以继续使用原名称。两个容器内部的路径也可以相同，关键是不能映射到同一份宿主数据或同一个可写卷。

无需为第二实例全局替换品牌、Python 包名、CLI 名、环境变量名、数据库表名或迁移脚本。应使用项目实际支持的配置与独立部署文件实现隔离。

SQLite 数据库文件即使名称相同，只要实际位于不同数据目录，也不构成冲突。PostgreSQL 可以复用服务进程，但必须使用独立数据库与最小权限账号，而不是让两个实例连接同一个业务数据库。

## 四、给部署 Agent 的完整提示词

使用方法：将**第三节已确认参数表与下面代码框一起**复制给能够访问目标服务器的 Agent，不要只复制代码框而遗漏参数。先完成只读盘点；无冲突且不需要未授权的主机级变更时继续部署，不重复等待同一套名称确认。

```text
任务：在已经运行一套本平台的服务器上，新增一套独立的用户体验/测试平台。

源码优先使用用户交付的源码 ZIP，先校验其 SHA-256，再运行包内 deploy/ubuntu/verify-source.py。
不要用 git pull 或其他仓库覆盖已交付快照。若用户明确选择从 Git 获取源码，
仓库为 https://github.com/whl736989911/AI-MAITU，使用 develop 的独立副本并记录实际 SHA。
新实例使用随提示词提供的已确认 aiway-trial 参数表；品牌为麦途 / AIWAY，默认强调色 #4F46E5。
平台域名 https://ai.xiaocar.cn，帮助与反馈目标为 https://ai.xiaocar.cn/help。

这不是升级、迁移、恢复或接管现有平台。允许共享机器资源，但要求配置、业务数据、
登录状态、授权身份及日常运维互不串用。
不要承诺仅凭不同目录和端口就具备完整安全隔离。

【第一阶段：只读调查，不安装、不启动、不修改现有服务】

1. 检查服务器系统及现有平台的实际部署方式：
   - 源码目录、源码版本、Python 环境或容器镜像。
   - 服务用户、HOME、MAITU_HOME、兼容的 OCTOP_HOME。
   - systemd 服务及 drop-in，或 Compose 项目、容器、网络、卷。
   - 监听端口、反向代理、域名、TLS。
   - 数据库、数据目录、Agent 工作区、知识库、附件、日志及备份。
   - 授权身份目录、更新队列、更新器服务、定时任务。
   - 外部存储、机器人、OAuth、浏览器及设备接入。

2. 读取当前源码中的部署脚本、Compose、入口脚本和路径解析逻辑。
   不要因为脚本叫“安装”就直接执行。
   特别检查固定服务名、固定容器名、镜像标签，以及升级/授权脚本会重启哪个服务。

3. 输出“旧实例实际值 / 已确认参数表中的新值 / 是否冲突 / 处理方式”清单。
   不展示密码、Token、私钥或完整含密连接串。无冲突后按已确认方案继续，
   不重复要求确认同一套名称；发现实际冲突、缺少必要授权或需要额外主机级变更时再暂停询问。

【第二阶段：盘点无冲突后，仅部署新实例】

必须遵守以下约束：

1. 旧实例保护
   - 不停止、不重启、不升级、不迁移旧实例。
   - 不覆盖其源码、环境文件、配置、数据、服务文件、镜像标签及授权身份。
   - 不对旧目录执行递归 chown/chmod，不清理旧容器、网络、卷。
   - 禁止全局 prune、按模糊名称批量停止进程或容器。
   - 不修改全局 Python 环境，不全局安装/升级本项目。
   - 不擅自升级系统软件、重启 Docker、修改全局安全策略或重启服务器。
   - 如确有必要进行可能影响旧平台的主机级操作，单独说明影响并等待授权。

2. 源码与依赖
   - 优先解压并验证用户交付的源码包，记录包校验值，不用远端源码覆盖它。
     只有用户明确选择 Git 来源时才获取 develop 的独立副本并记录实际提交 SHA。
   - 本地构建本项目，不替换为上游 PyPI 包或其他仓库版本。
   - 原生部署使用独立虚拟环境并安装 `office,knowledge-ocr,local-embedding` extras；Ubuntu 系统依赖包含 `libgl1`（opencv-python 的 `cv2` 需要 libGL）及 `libglib2.0-0`。
   - 不做全局品牌替换，不修改 Python 包名、CLI 名或受支持的环境变量名。
   - 若部署脚本不能安全指定第二实例，使用独立部署配置或独立服务文件，
     不以 --force 覆盖旧服务，不临时改动旧平台文件来迁就新部署。

3. 持久化与数据库
   - 容器内 MAITU_HOME / OCTOP_HOME 均设为 /data/.octop，
     仅绑定新宿主目录 /var/lib/aiway-trial；原生备用方案均设为 /var/lib/aiway-trial。
   - 检查最终实际生效的路径，不只检查配置文本。
   - 检查绝对路径、符号链接、bind mount、共享卷及外部存储，
     避免两个名称指向同一份数据。
   - 新实例可写状态不得落入旧实例的源码、数据或备份目录。
   - 不复制旧数据库、账号、聊天记录、知识库、附件及业务配置作为测试种子。
   - SQLite 使用新数据目录内的新数据库。
   - PostgreSQL 可以复用数据库服务进程，但必须使用独立数据库及最小权限账号，
     不连接或迁移旧平台数据库。
   - 确认重建容器后业务数据、授权身份仍然保留。

4. 运行与访问隔离
   - Docker 必须隔离 Compose 项目、显式 container_name、镜像标签及可写卷；
     仅添加 -p 项目名不足以消除显式容器名冲突。端口绑定为 127.0.0.1:18088:8088。
   - 所有 Compose 运维命令固定使用新实例的项目名、配置文件及环境文件。
   - 原生部署使用独立非 root 服务账号、独立 systemd unit 和绝对 ExecStart。
     不使用可能固定操作 maitu.service 的通用 service 命令管理第二实例。
   - 使用独立测试域名，核对 API、WebSocket、SSO 回调、PWA 与浏览器存储隔离。
     检查 Cookie Domain，避免宽泛父域 Cookie 导致共享登录状态。
   - 如共用反向代理，仅新增测试站点；先检查配置，再安全 reload，不覆盖原站点。
     对共享反向代理的变更必须在已确认的部署方案范围内。
   - 防火墙只追加新实例所需的最小规则，不关闭或重置现有防火墙。
   - 检查所有辅助端口，不能只检查主 HTTP 端口。
   - 不占用旧实例的桌面会话、浏览器调试端口、ADB 或其他物理设备。

5. 授权与外部接入
   - 新平台初始化独立实例身份并单独合法激活。
   - 不复制旧实例私钥、激活凭据、JWT 签名材料或更新客户端令牌。
   - 可以使用同一授权中心及其公开验签材料，但不能共用实例身份。
   - 不另行部署授权中心，除非我明确要求。
   - 更新器、更新队列、备份恢复及清理任务只能作用于新实例。
   - 不复用旧机器人的长连接凭据，不覆盖旧 OAuth 应用回调。
   - 外部对象存储、检索库等使用独立可写命名空间及最小权限凭据。
   - 不需要的外部接入保持关闭。

6. 体验用户安全
   - 不默认授予平台管理员、宿主管理、共享目录写入或高危工具权限。
   - 不把 root、sudo、宿主 Docker socket、生产目录或生产凭据暴露给体验用户。
   - 如启用终端/代码执行，必须限制在测试实例的隔离环境内，
     核验其不能访问生产文件、管理接口或生产数据库。
   - 独立 Docker 网络不等于禁止访问宿主及生产网络；按实际需求限制网络访问。
   - 真实桌面、宿主执行、宿主 Docker 等能力默认关闭。
   - 如体验需求必须允许不可信用户操作宿主，先提出独立虚拟机方案，
     不通过特权容器、关闭安全机制或复用生产服务账号绕过隔离。

【第三阶段：实际验收，不能只说“启动成功”】

1. 依赖必须逐项核验并补齐：在 venv 内执行
   octop doctor --require "$EXTRAS"（安装脚本已自动执行一次；升级或换机后要再跑）。
   报告缺失的组件、缺失的导入或外部命令，以及缺失的系统包；
   有 root 权限时可加 --fix 自动 apt 安装，否则输出并执行对应安装命令。
   至少确认：本地向量依赖（fastembed / huggingface_hub）、
   OCR（rapidocr / onnxruntime / cv2，其中 cv2 需要 libgl1、libglib2.0-0）、
   office（pdfplumber / pandas）；启用的其他能力同样要核验。
   缺依赖时不得宣称部署完成。
2. 记录部署前后旧平台的健康状态、容器或服务运行状态和重启计数；
   在具备授权的情况下验证旧平台关键功能，不修改其业务数据。
3. 在新平台创建专用测试账号、Agent、会话及测试文件，
   证明它们实际写入新实例的数据库和挂载目录。
4. 验证新旧平台登录状态不互相覆盖，新实例 Token 不能访问旧实例受保护接口。
   涉及旧平台的验证仅使用无副作用请求。
5. 验证体验账号的后端权限，而非只检查页面是否隐藏。
6. 仅重启新实例，验证其数据持久化且旧实例未重启、仍可访问。
7. 证明停止、更新、回滚、备份、恢复及删除新实例的命令均只定位新实例。
   不对旧实例执行破坏性测试；删除和恢复仅提供命令及影响范围，不擅自执行。
8. 无法验证的项目明确列为“未验证”，不得用推断代替结果。

最终交付：
- 新实例源码提交 SHA、访问地址、服务名或 Compose 项目名。
- 新实例目录、端口、挂载、数据库、授权身份和外部接入清单。
- 仅针对新实例的启动、停止、日志、更新、备份及回滚命令。
- 实际验收结果、未验证项、涉及的共享基础设施及剩余风险。
- 管理员凭据通过安全方式交付，不写入聊天、仓库或普通部署日志。

现在先执行只读盘点并输出冲突对照表。无冲突后按已确认参数表继续部署；发现实际冲突或需要额外授权时再暂停询问。
```

## 五、执行与验收记录要求

本次命名已经确认，但必须完成服务器只读冲突盘点后才能部署；需要改变已确认值、影响旧实例或进行额外主机级变更时须另行取得授权。部署成功不能只以进程存在或健康接口返回成功为依据。交付记录应包含实际路径与挂载、独立数据库、`octop doctor --require` 的逐项结果（缺失依赖及其安装结果）、持久化结果、登录与权限验证，以及旧平台未被重启或修改的证据。

需要旧平台账号或其他额外授权才能完成的检查，应先取得授权；无法完成的检查明确标记为“未验证”。文档中的建议、提示词和命名表本身都不是目标服务器已经隔离成功的证据。
